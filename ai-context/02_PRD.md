### 0.4 四条硬声明

1. **凡标「待确认」的，不得写死进代码**。V0.2 曾把「D 组与 A 组同级」和「全部 A 组闭环才冻结」同时写进规则，自相矛盾（`AC-07`），V0.3 已拆开。
2. **凡标「建议值」的，是本文给的默认值**，业务方确认前不算定论。
3. **消防阈值分两层**：国标值用于「是否合法」，培训值用于「是否达公司标准」。二者不互相替代，混用会导致误判（详见附录 A）。
4. **本文所有容量、单价、体积、时限、名单均为「建议值 / 估算」**（§4.9、§5.2.8、附录 H），业务方确认前不得写死进代码；云厂商单价随地域与活动变动，须以采购当期报价复核。

## 1. 项目概述

### 1.1 背景与范围

园区物业管理当前依赖**纸质打勾表 + Excel 台账 + 微信群催办**：消防整改压力大、留痕分散、月底统计靠人肉汇总 `[L-M7][M-02][M-03]`。2026-11-17 消防专项培训后，巡查体系明确为**日 / 周 / 月三级**，并新增大批带数值阈值的消防检查项，原「点位 + 路线顺序打卡」模型不再适用 `[L-R1][L-M11]`。

**一期范围（`L-C3` 已确认）**：

| 模块 | 是否一期 | 登录门槛 | 依据 |
|---|---|---|---|
| 随手拍（问题上报） | ✅ 一期自研 | **微信登录（L1 即可）**，L2 亦可用 | `L-C3`、`U-D2` |
| 巡查（**二维：日常/消防 × 日/周/月** + 检查项字典） | ✅ 一期自研 | **必须企微登录（L2）**，L1 不可进入 | `L-C3`、`L-D1`、`U-D1`、`U-D7` |
| 报修工单（含派发） | ✅ 一期自研 | L2 派单/验收；L1 仅可提交与查自己工单 | `L-C3`、`§4.8.4` |
| 物品放行 | ⬜ backlog（有纸质单，成本低） | L1 / L2 均可申请 | `L-C6` |
| 日常任务 | ⬜ backlog（月度计划表已有 41 条） | L2 | `L-C6`、`S-03` |
| 会议预约 | ⬜ backlog（无现状） | L1 / L2 | `L-C6` |
| 投诉建议 | ⬜ backlog（考核指标已存在） | L1 / L2 | `L-C6`、`S-04` |
| 数据大屏 / 水电数云 | ❌ 移出一期（`L-C1` 预留接口） | — | `L-C1` |

**「商户」定义已澄清（`L-C2`）**：指**园区企业**（46 家），不含访客、不含外部人员。

**登录模型已定（`U-D1`~`U-D5`）**：一期主入口 = **企业微信工作台 + 双环境适配**（不勾「仅在企业微信运行」）；内部人员用企微身份（L2），商户用微信登录（L1）并绑定企业档案，**企微身份权重高于微信身份**。完整判定、门禁与合规见 §4.8。

**巡查分类已定（`U-D7`）**：巡查按内容分**日常巡查**（公共区域异常、可疑人员）与**消防巡查**（消防器材、商户内部隐患、消防整改完成情况、园区大型设施运转）；与原有「日/周/月」频次**正交**，构成二维模型。详见 §5.2.0、§5.2.6。

### 4.2 巡查任务状态机

```
PENDING ──开始──> IN_PROGRESS ──提交──> PENDING_REVIEW ──通过──> APPROVED
   │                    │                      │
   │                    │                      └──驳回──> REJECTED ──重提──> PENDING_REVIEW
   └──超时──> OVERDUE <──超时──┘                   
                  │
                  └──补录(需审批)──> IN_PROGRESS
```

| 约束 | 规则 |
|---|---|
| 开始条件 | 在任务时段内（可提前 15 分钟） |
| 提交条件 | 必填项齐全（见 §5.2.3） |
| 复核 | **操作人 ≠ 提交人**，系统强制校验 |
| 补录 | 需填原因 + R2 审批；补录后仍计入逾期率 |
| 作废 | 仅 R4，需填原因 |

**三组指标口径（`AG-23`）**：

| 指标 | 分子 | 分母 | 排除 |
|---|---|---|---|
| 准时完成率 | `APPROVED` 且提交时间 ≤ deadline | 应完成任务数 | `VOID` |
| 任务完成率 | `APPROVED` | 应完成任务数 | `VOID` |
| 逾期率 | 曾进入 `OVERDUE` | 应完成任务数 | `VOID` |

> **关键设计**：补录通过后仍计入逾期率，否则补录就是洗白通道。

### 4.3 异常分级与整改闭环

| 档位 | 判定 | 处置 | 时限（建议） |
|---|---|---|---|
| **红线** | 见下方 8 条 | 强制建工单 + 即时通知 R4 + 下发整改通知书 | 24 h |
| **一般** | 非红线的不合格 | 下发整改通知书 | 7 d |
| **观察** | 轻微/可现场纠正/标准待核 | 只记录，不转单 | 连续 3 次 → 升一般 |

**红线项 8 条**（依据 `L-R2`+`M-02`+`S-04`）：消防通道/疏散通道被占用（<1.4m）、消火栓无水或被圈占、配电房异响或配电箱前堆物、危化品超量（>3–5 桶或 >80kg）、安全出口锁闭封堵、防火门被拆除/常闭失效/等级不符、喷淋头被喷涂损坏、消防报警未 3 分钟到场。

**状态流**：`待分级 → 已分级 → 已下发 → 整改中 → 待复查 → 已关闭`，其中：
- 复查不通过 → 退回「已下发」，期限顺延并记次数
- 逾期 → 「已升级」，通知 R4
- **红线不可降级为观察，不可由 R2 单独关闭**

### 4.4 工单状态机与「双方确认」

「双方确认」与开发计划的「独立验收」**不矛盾，是两种模式**：

| 模式 | 适用 | 验收要求 |
|---|---|---|
| `internal` 单方验收 | 内部工单 | 派单人/主管验收 |
| `joint` 双方确认 | 外协工单 | **处理方签认 + 物业方签认，两签齐全才可完成** |

状态流：`待派单 → 待接单 → 处理中 → 待验收/待双方确认 → 已完成 → 已归档`

**硬约束**：`joint` 模式下 `signature_count` 必须 = 2 才能完成。缺一方就停在「待双方确认」并计时——这条防的是「外协自己点完成、物业没到现场」。

### 4.8 身份、登录与权重（V0.3.1 新增 · 已决策）

> 本节来自用户 2026-11-24 17:00 的 5 条拍板（`U-D1`~`U-D5`），是本版唯一新增的决策章节。凡本节标「待确认」的，仍不得写死进代码（§0.4）。

| 编号 | 用户原话 | PRD 落地 |
|---|---|---|
| `U-D1` | 巡查功能必须登录企业微信的人才能用 | 巡查模块 L2 门禁（§4.8.4） |
| `U-D2` | 随手拍必须登录微信 | 随手拍以有效 `openid` 为最低门槛（§4.8.4） |
| `U-D3` | 用企微登录的人权重大 | 新增 `auth_level ∈ {L1, L2}`，L2 > L1（§4.8.3） |
| `U-D4` | 一期主入口：企微工作台 + 双环境适配 | 不勾「仅在企业微信运行」，双通道登录（§4.8.2） |
| `U-D5` | 商户用微信登录即可 | R7 开 L1 账号 + 后台审核绑 `enterprise_id`（§4.8.2） |

#### 4.8.1 两条必须先讲清的技术事实

1. **「企业微信登录」不是一种登录方式，而是运行环境**。小程序只有在**企业微信客户端内**打开时才能调 `wx.qy.login`；在普通微信里打开，该接口不存在，拿不到企微 `userid`。微信官方技术支持的原话是「微信环境不能使用 `wx.qy.login`」（`WX-05`）。
2. **企微内 `wx.login` 依然可用**。企业微信内置的是微信同款小程序引擎，企微环境下调 `wx.login` 拿到的是该用户的微信 `openid`。所以**企微员工天然同时持有 `userid` 和 `openid`**——「随手拍需微信登录」对内部员工不构成障碍，巡查员在企微里发现异常照样能拍照上报。

> ⚠️ 若把 `U-D2` 严格读成「只有微信登录的人才能用随手拍、企微登录者不可用」，则巡查员在企微里无法上报异常，§4.3 的整改闭环当场断掉，且与 `FR-29`（随手拍是报修来源之一）冲突。本文按「**随手拍的最低门槛是有效 openid，L2 因同时持有 openid 自动满足**」实现，并把该解释列入 §13 `U2` 待业务确认。

#### 4.8.2 双环境判定与登录链路

| 运行环境 | 判定方式 | 可调用接口 | 取得的身份 | `auth_level` |
|---|---|---|---|---|
| 企业微信工作台（主入口） | `wx.getSystemInfoSync().environment === "wxwork"` | `wx.qy.login` **+** `wx.login` | `corpid` + `userid` **且** `openid`/`unionid` | **L2（高）** |
| 微信（聊天 / 扫码 / 搜索） | 无 `environment` 字段 | 仅 `wx.login` | `openid` / `unionid` | **L1（低）** |

**后台链路（4 步）**：

1. `wx.qy.login` → `code` → 企业微信 `cgi-bin/miniprogram/jscode2session` → `userid` / `corpid`。**access_token 必须用「与该小程序关联的企微自建应用 secret」换取，不能用小程序 appid/secret**（`WX-03`）。
2. `wx.login` → `code` → 微信 `jscode2session` → `openid` / `unionid`。
3. 写 `identity_bindings`：`userid ↔ openid ↔ users.id`。一人一条主记录，两个身份指向同一个 `users.id`，**不建两套账号**。
4. L1 账号处理：内部员工若 `openid` 已绑定 `qy_userid` → 判定为「L2 账号处于 L1 会话」，走 §4.8.5 引导；未绑定的 L1（商户）→ 进「待审核」池，由运营后台审核并绑定 `enterprises.id`（46 家档案），绑定前只能看说明页与公告。

> 依据：`WX-01`（环境字段）、`WX-02`（`wx.qy` 仅企微可用）、`WX-03`（code2Session 返回 userid）、`WX-04`（上架与「仅企微运行」）、`WX-05`（微信环境禁用 `wx.qy.login`）、`WX-06`（外部联系人拿不到本企业 userid）。

#### 4.8.3 身份权重等级 `auth_level`

「权重」是业务口语，PRD 必须落成可判定字段。本文定义为 **`auth_level ∈ {L1, L2}`**，L2 > L1，体现在 5 个维度：

| 维度 | L2 企微身份（高权重） | L1 微信身份（低权重） |
|---|---|---|
| 可用功能 | 巡查全链、随手拍、工单派单/验收、整改下发、复核、关单、报表 | 随手拍、物品放行申请、投诉建议、会议预约、查看自己提交的工单 |
| 数据范围 | 按角色：本部门 / 全园区 / 本人 | 仅 `enterprise_id` 绑定范围内 + 本人提交 |
| 留痕效力 | 打勾、复核、下发整改单、关单、双方确认签名**有效** | 仅提交与查看；**不可复核、不可关单、不可签发整改单** |
| 实名与防作弊 | 企微组织架构实名 + 服务端校验 `userid` 有效性 | `openid` + 后台绑定审核（**不强制手机号**） |
| 统计口径 | 计入巡查覆盖率 / 准时完成率 / 考核 | 不计入物业绩效，单列「商户上报量」 |

**两条边界**（防止权重概念被滥用）：

- `auth_level` **与 RACI 角色正交**：角色决定「做什么动作」，等级决定「能不能进这个模块」。例：R2 队长在微信里打开（L1 会话）仍不能复核，必须回企微。
- **不建议用 `auth_level` 给异常记录排序**（如「企微上报优先处理」）。那会与 §4.3 分级规则、§4.2「复核人 ≠ 提交人」打架。若业务确需优先级，另建 `source_priority` 字段，不复用 `auth_level`。→ §13 `U1` 待确认。

#### 4.8.4 功能门禁矩阵

| 功能 | L2 | L1 | 服务端校验点 |
|---|---|---|---|
| 巡查任务领取 / 打勾 / 提交 | ✅ | ❌ | `qy_userid` 存在、有效、属当前 `corpid` |
| 巡查复核 / 作废 | ✅（且需 R2 / R4） | ❌ | 角色 + L2 双校验 |
| 异常分级 / 下发整改通知书 | ✅ | ❌ | 角色 + L2 |
| 工单派单 / 验收 / 双方确认 | ✅ | ❌ | 角色 + L2 |
| **随手拍（问题上报）** | ✅ | ✅ | 仅需有效 `openid` |
| 物品放行申请 | ✅ | ✅ | L1 只能提自己 `enterprise_id` 的单 |
| 投诉建议 / 会议预约 | ✅ | ✅ | 数据范围过滤 |
| 报表 / 导出 | ✅（R4 / R5 / R6） | ❌ | 角色 + L2 |
| 查看自己提交的记录 | ✅ | ✅ | 数据范围过滤 |

> **门禁必须做在服务端**（`FR-54`），前端隐藏菜单不算门禁。`qy_userid` 每次会话需向企微接口校验有效性，防离职 / 调岗后残留权限；校验失败降为 L1 并写 `audit_logs`。

#### 4.8.5 微信端降级与引导（不硬拒绝）

员工在微信里打开、且 `openid` 已绑定 `qy_userid` 时：

1. 首页展示使用范围说明 + 「**请从企业微信工作台打开以使用巡查功能**」的引导，**不弹「无权限」错误页**；
2. 随手拍、投诉建议、会议预约等 L1 功能照常可用；
3. **不提供「在微信里补一个企微登录」的入口**——技术上做不到（§4.8.1），做了就是骗人；
4. 该次会话记为 L1，`audit_logs` 记录降级原因，便于后续统计「有多少人从微信误入」。

#### 4.8.6 合规三条件与手机号

按微信《小程序帐号登录规范要求与修改指引》（`WX-07`），本项目属 **「体验范围特定」**（内部员工系统 + 已备案园区企业），**允许首页即做账号鉴权**，但必须同时满足 3 条：

| # | 平台要求 | 本文落地 |
|---|---|---|
| 1 | 首页有**明显的使用范围说明** | 首页固定文案：「本系统仅限金峰兆业时尚产业社区物业内部人员及已备案园区企业使用」 |
| 2 | 首页即做**账号鉴权** | `app.js` 静默取 `wx.login` / `wx.qy.login`，不弹授权框 |
| 3 | 提供**「暂不登录 / 取消登录」**选项 | 首页保留「暂不登录，先浏览」按钮，可看说明页与公告 |

**明确不做**（违反即审核被拒，`WX-08`）：

- 一进入就弹手机号授权；
- 隐私协议默认勾选，或写「登录即代表同意」；
- 用户拒绝授权就拒绝提供全部服务；
- 强制收集手机号。

> `wx.login` 是**静默**的，不产生授权弹窗，不属于「授权登录」规范约束范围。内部靠 `userid`、商户靠后台审核绑定，两者都不需要手机号 → 一并规避企业认证、隐私指引声明、按次计费（快速验证组件免费额度用尽后约 0.03 元/次）、审核风险四件事。

### 4.9 现场问题上报分级与应急响应（V0.3.4 新增）

> 来自用户 2026-11-24 提问：问题上报分几个等级、每级对应措施、最严重等级是否提示拨主管电话、每级给现场人员示例。**本节是「现场上报紧急度」规则**，与 §4.3「整改档位」（红线 / 一般 / 观察）是上下游两个字段，不互相覆盖（见 §4.9.4）。全部时限 / 名单 / 号码为**建议值**（§0.4），不得写死进代码。

#### 4.9.1 为什么是 4 档，不是沿用 §4.3 的 3 档

§4.3 三档里「红线」内部跨度过大：`消防通道被纸箱临时占用` 与 `配电箱冒烟 / 明火` 同归红线，但前者是 24 h 整改、后者要立即疏散并电话上报。若继续用 3 档，最紧急情形只能靠人工额外判断，容易漏报。故**上游上报拆 4 档**，把「立即打电话 + 启动应急预案」从「24 h 整改」里独立出来。3 档方案已评估但不采用（无法区分「立即处置」与「限时整改」）。

#### 4.9.2 四档定义与对应措施

| 档 | 名称 | 色标 | 判定（现场视角） | 响应 / 闭环时限（建议） | 通知对象 | 系统强制动作 | 拨主管电话 |
|---|---|---|---|---|---|---|---|
| `L1` | 提示 | 蓝 | 脏乱 / 小瑕疵，不影响安全，顺手可记 | 纳入日常保洁，7 d 内 | 巡查人 + 班组 | 只记录 + 拍照；**不建整改单**；连续 3 次自动升 `L2`（沿用 §4.3 观察规则） | 否 |
| `L2` | 一般 | 黄 | 需要整改，但不会马上出事 | 24 h 派单 / 7 d 闭环 | R2 复核人 + R3 派单 | 建异常单 → 下发整改通知书 → 到期提醒 → 复查 | 否 |
| `L3` | 严重 | 橙 | 命中 §4.3 红线 8 条 / 碰消防与大型设施 / 商户违规 / 整改逾期 | 2 h 内响应 / 24~48 h 闭环 | R2 + R3 + **R4 知会** | 现场先管控（隔离 / 停用 / 劝离）→ 强制建单 → 企微即时推送 → 复查计次；**不可降级为观察、不可由 R2 单独关闭**（§4.3） | 否（可配置开启） |
| `L4` | 紧急 | 红 | **正在发生**且可能伤人 / 着火 / 大面积停摆 | ≤5 min 响应，即时 | R4 + 项目负责人 + 值班主管（电话） | **先拨 119/120（如涉及）→ 一键拨值班主管 → 启动附录 B 应急预案 → 疏散 / 断电 / 警戒 → 自动建 L4 事件单 + 企微全员通知 + 拨打留痕** | **是，强制弹窗** |

> 色标沿用红 = 最严重，与国内物业 / 消防现场标识一致。

#### 4.9.3 三问法（现场工作人员分级指引）

上报页固定浮层 + 帮助页同一套文案，按顺序问：

1. **是否正在发生、可能伤人 / 着火 / 大面积停摆？** → 是 → `L4 紧急`（先报警 / 急救，再拨主管）
2. **是否碰了消防、电房 / 大型设施、商户违规，或整改已逾期？** → 是 → `L3 严重`（先管控现场，立即上报）
3. **是否需要整改、但不马上出事？** → 是 → `L2 一般`（拍照下单，限期整改）
4. 只是脏乱 / 小瑕疵、顺手能记 → `L1 提示`

**两条硬口诀**：① **拿不准往高报一级，由 R2 复核降档；严禁往低报**；② 现场人员只判 `report_level`，**不判**「是否红线」——红线是 R2 复核后的 `rectify_level`，避免让一线承担合规定性责任。

#### 4.9.4 与 §4.3 三档的映射（不改 §4.3）

| `report_level`（R1 现场判） | → `rectify_level`（R2 复核定） | 说明 |
|---|---|---|
| `L1 提示` | 观察 | 连续 3 次 → 一般 |
| `L2 一般` | 一般 | 直接建整改通知单 |
| `L3 严重` | 红线（命中 8 条）/ 一般（未命中但仍属设施 / 商户违规） | R2 按 §4.3 红线 8 条逐条比对后落档 |
| `L4 紧急` | 红线 + 应急预案事件 | 单列 `emergency_events`，除整改单外另走附录 B |

**改级留痕**：R2 复核可调整 `report_level`，必填 `level_override_reason`（≥10 字），写 `audit_logs`，前端展示「原报 L3 → 复核改 L2」。`FR-90`。

#### 4.9.5 最严重档（L4）要不要提示拨主管电话 —— 要，但按下面 7 条落地

结论：**要**。理由：`wx.makePhoneCall` 在微信与企微小程序**双环境均可用**（`WX-11`），L4 争的是分钟级响应，企微消息可能被淹没，电话是最可靠的一跳。但不能只放一个电话按钮，须满足：

| # | 设计 | 原因 / 依据 |
|---|---|---|
| 1 | **L4 提交前二次确认**弹窗：「此为紧急上报，将立即通知值班主管并调起拨号」，30 s 内可撤销 | 防误报骚扰主管 |
| 2 | 确认后弹**不可一键划走的提示条**，主按钮「一键拨打值班主管」，次按钮「已通知，稍后联系」 | 强制触达，但保留不拨的出口 |
| 3 | 号码**不写死在客户端**：服务端下发值班主管白名单（主 / 备 / 第三联系人，含姓名 + 岗位 + 号码） | 排班轮换、人员变动不改代码；`U9` |
| 4 | **火情 / 人身伤害优先提示 119 / 120，再拨主管**（两个按钮并列，119/120 在上） | 合规顺序，不能先内部汇报再报警 |
| 5 | 拨打**同时**自动建 L4 事件单 + 企微消息推 R4 + 写 `phone_call_logs`（拨打时间、目标、结果） | 避免「打了电话但没留痕」，事后无法追责 |
| 6 | 主管未接 / 占线 → 提示转第二联系人，终点刘振强（R4）；`wx.makePhoneCall` **只能唤起拨号盘、需用户确认**，不能自动外呼 | `WX-11`、§4.5 升级链 |
| 7 | **仅 L4 弹电话**；L3 只做企微即时推送（是否也提示电话设为可配置项，默认关） | 避免天天弹电话导致脱敏 |

**iOS 体验提示**：`wx.makePhoneCall` 在 iOS 上常仅顶部显示拨号横幅、需用户再点一次，按钮下方须写「点击后将调起拨号，请在顶部横幅确认拨打」，避免现场人员以为没反应（`WX-11`）。

#### 4.9.6 每档简要示例（现场速查，配置化可改文案）

| 档 | 示例（关联检查项 / 子域） | 现场一句话口诀 |
|---|---|---|
| `L1` 提示 | 公区少量纸屑 / 落叶、墙面小面积污迹（`DO-01`）；一盏非疏散指示灯不亮（`DO-02`）；灭火器箱体轻微积尘但压力正常（`EQUIPMENT`）；草坪少量杂草 | 「不影响安全，记一笔，交给保洁」 |
| `L2` 一般 | 消防通道被纸箱临时占用但仍 ≥1.4 m、手推车靠边停放（`EQUIPMENT` / `DO-01`）；灭火器压力表在黄区、单只应急灯不亮（`EQUIPMENT`）；商户内少量纸箱靠墙、未堵疏散（`TENANT`）；整改到期但尚未逾期未复查（`RECTIFY`） | 「要整改，但不马上出事 → 拍照下单」 |
| `L3` 严重 | 命中 §4.3 红线 8 条（疏散通道 <1.4 m、消火栓被圈占、配电箱前堆物、安全出口锁闭、防火门常闭失效、危化品超量、喷淋头被喷涂、报警未 3 min 到场）；商户私拉乱接 / 阁楼堆高超限 / 大量易燃品（`TENANT`）；整改通知书逾期或复查不通过（`RECTIFY`）；**G1 高低压电房异响 / 异味、G2 消防主控故障或屏蔽点未处理**（`FACILITY`） | 「碰消防、电房、商户违规，或整改拖了 → 先管控再上报」 |
| `L4` 紧急 | 明火 / 冒烟 / 燃气味；电线打火、配电箱冒烟；消防主机报警并确认险情；人员受伤 / 被困 / 坠落、电梯困人；大面积漏水淹及电房；可疑人员正在实施破坏 / 盗窃 / 暴力（`DO-03` → `security_incidents`） | 「正在出事、会伤人着火 → 先 119/120，再一键拨主管，按预案疏散」 |

> **分流约束**：可疑人员类（`DO-03`）即便判 `L4` 也**不自动生成整改通知单**，走 `security_incidents` + 上报秩序值班室；是否报 110、是否联动门禁监控仍按 §13 `U7` 由物业定。照片含人脸按 `WX-08` 敏感个人信息处理（§5.2.8）。

> 全部示例文案存 `report_level_config` 表，业务方可后台改文案与阈值，**不改代码**（`FR-87`）。

### 5.2 巡查（一期核心）

#### 5.2.0 巡查二维模型（V0.3.3 新增 · 用户定义）

> 用户 2026-11-24 给出巡查分类（`U-D7`）：巡查分**日常巡查**与**消防巡查**，各有明确检查对象。本小节把它落成可与现有「日 / 周 / 月」共存的**二维模型**，并消除「日常」一词的双义。

**维度 A · 巡查类型 `patrol_type`（内容域，本版新增）**

| 类型 | 枚举 | 检查对象（用户原话） | 落点 |
|---|---|---|---|
| 日常巡查 | `DAILY_ORDER` | 公共区域是否有异常、是否有可疑人员 | §5.2.0.1、附录 G |
| 消防巡查 | `FIRE` | ① 消防器材是否损坏 ② 商户内部是否有消防隐患 ③ 消防整改是否完成 ④ 园区大型设施（高低压电房、消防主控等等）是否正常运转 | §5.2.6、附录 G |

**维度 B · 频次 `frequency`（沿用 §5.2.2，本版改称「日 / 周 / 月频次」）**

`DAILY`（早 / 晚两班）、`WEEKLY`、`MONTHLY`。**频次回答「多久做一次」，类型回答「查什么」，两者正交**：任一类型都可配任一频次，不做硬绑定（默认，见 §13 `U5`）。

**任务生成**：`patrol_task = patrol_type × frequency × target × check_item_set`；`checkItemsSnapshot` 按「类型 + 频次」双键快照（`FR-09` 扩展）。同一班次可同时领到一张 `DAILY_ORDER` 任务与若干张 `FIRE` 任务，界面需按类型分组，不许混在一张表里打勾。

> ⚠️ **术语消歧（`AC-11`）**：V0.3.2 及以前，§5.2.2 把早 / 晚两班的**频次级别**叫「日常巡查」；本版起该词专指**内容类型**（`DAILY_ORDER`）。频次级别统一改称「日频次 / 周频次 / 月频次」，§9.2、§10 中的「日常巡查」已按新义复核改写。

**5.2.0.1 日常巡查（秩序安防）检查项集 —— 现有 30 项字典的空白**

附录 A 的 30 项几乎全为消防项，`DAILY_ORDER` 的两类对象在字典里**没有对应条目**，须新增（另起 `DO-xx`，不挤占消防 30 项编号）：

| 编号 | 检查对象 | 检查项 | 结果形态 | 异常处置 |
|---|---|---|---|---|

#### 5.2.7 打卡分期方案（V0.3.4 新增）

> 用户 2026-11-24 决策：**一期只做拍照水印打卡；二期增加 NFC、二维码扫码打卡**。本节固定分期边界、平台约束与字段预留；图片规格见 §5.2.8。
>
> **术语消歧（`AC-10` 关闭）**：本版起「**打卡**」专指到点位签到（即清单 1.4 旧称的「随手拍：点位与路线顺序打卡」），「**随手拍**」专指问题上报时的现场取证照（§1.1 义）。`AC-10` 双义按此关闭；`U2` 保留但收窄为「随手拍 = 问题上报，最低门槛 openid」，不再含打卡义。

##### 5.2.7.1 分期边界

| 期 | 打卡方式 | 硬件 | 平台覆盖 | 状态 |
|---|---|---|---|---|
| **一期** | `PHOTO_WATERMARK` 拍照水印 | **不部署**：点位为系统内「逻辑点位」（`check_points`），仅用于水印地点、任务生成与 GPS 粗校验 | 微信 + 企微双端、iOS + Android 全覆盖 | **本版范围** |
| **二期** | 增加 `NFC` / `QRCODE` / `COMBINED` | 贴 NTAG213/215/216 标签 + 静态二维码 | NFC **仅 Android**；二维码双端 | 仅预留模型与字段，不实现 |

##### 5.2.7.2 一期打卡链路（必须遵守的防作弊约束）

```
进入巡查任务（L2 门禁）→ 服务端下发一次性 checkin_token(point_id / 时间窗 / 随机串)
→ wx.createCameraContext().takePhoto() 实时取帧（禁相册）
→ canvas 叠加服务端水印模板 → wx.compressImage(q=80) → 上传
→ 服务端：校验 token 一次性 + 时间偏差(>5min 告警) + 点位/GPS 一致性 + 原图 SHA-256 入库
→ 转 WebP + 生成缩略图 → 丢弃客户端 JPEG → 写 checkin_records
```

| 约束 | 规则 | 依据 |
|---|---|---|
| 禁相册 | 打卡照一律 `takePhoto`；`is_album=true` 服务端拒收 | `WX-10`、§4.6 |
| 水印内容 | 服务端时间（校准后）+ 点位名 / `point_id` + 人员姓名 / 工号 + 企业 + GPS + **签名短码**（由 `checkin_token` 派生） | §4.6 |
| 不承诺真实性 | 水印 / GPS 只做留痕参考，不承诺防作弊；客户端时间不信任，以服务端接收时间为准 | §1.3、§4.6 |
| 幂等 | 同一 `point_id` × 时间窗内重复提交只保留 1 张，秒级重复请求幂等 | `FR-60` |
| 门禁 | 打卡属巡查模块 → **仅 L2 企微身份**；随手拍（问题上报）→ 最低 `openid`（L1/L2 均可） | §4.8.4、`FR-62` / `FR-63` |

##### 5.2.7.3 二期 NFC / 二维码（仅设计，不实现）

| 项 | NFC | 二维码 |
|---|---|---|
| API | `wx.getNFCAdapter()` → `startDiscovery()` / `onDiscovered` | `wx.scanCode({ onlyFromCamera: true })`（基础库 1.2.0+） |
| 平台 | **仅 Android**（iOS 全系不支持，微信官方社区明确「iOS 不支持 nfc」） | 微信 + 企微小程序双端、iOS + Android |
| 标签 / 码 | NTAG213/215/216，只存 `point_id` + 随机校验串，**不写业务数据** | 静态码内容 = `point_id` + 短 TTL 动态串 |
| 防复制 | UID 可被克隆 → 必须配合一次性 `checkin_token` + 水印照 | 静态码可被拍照复制 → `onlyFromCamera:true` + 短 TTL 动态串 |
| 降级 | iOS / 无 NFC 机型 → 自动切二维码；二维码失败 → 回退拍照水印 | — |
| 单点成本（建议值） | 标签 ¥1~3/个 + 部署人工 | 码牌 ¥0.1~0.5/张 + 塑封 |
| 依据 | `WX-09`、`WX-10` | `WX-10` |

> **关键结论**：NFC UID 与静态二维码**都能被复制**（克隆 / 拍照代扫），所以二期**不取消拍照水印**。三者是组合关系而非替代：`NFC` / `QRCODE` = 「到场凭证」，`PHOTO_WATERMARK` = 「现场状态证据」；`checkin_method=COMBINED` 时两者都必填。
>
> **与 §1.3 / §7.4 不冲突**：二期贴的是**无源标签与静态码牌**，不是门禁 / 监控 / IoT 联网设备；§7.4 禁止的自动数据回传仍然不做。

##### 5.2.7.4 `AC-03` 的部分收敛

一期不部署硬件，打卡模型采用「**公区路线 + 逻辑点位**」（§13 原建议默认），楼层逐点模型**不采用**；物理点位数量、标签布点、二维码部署随二期确认 → `AC-03` 状态由「未解决」改为「一期已定、二期点位待定」（§12.2、`U10`）。

#### 5.2.8 图片规格与存储策略（V0.3.4 新增）

> 用户明确要求「考虑图片存储成本」，并区分两类用途。核心判断：**打卡图是「凭证」，随手拍是「证据」**——前者只要能证明人 / 时 / 地 / 点位，后者要能放大看清设备铭牌、压力表、隐患位置。两者不能用同一套参数。

##### 5.2.8.1 参数总表（建议值，业务确认前不得写死）

| 参数 | 打卡水印图 | 随手拍现场图 |
|---|---|---|
| 用途 | 证明「人 / 时 / 地 / 点位正确」 | 记录现场细节，供判责 / 整改 / 复核 / 取证 |
| 采集 | `camera` 组件 `takePhoto`，**禁相册** | `takePhoto` 为主；允许相册补图但须标 `is_album=true` 且**不作为到场证明** |
| 客户端上传份数 | **1 份**（已叠加水印的 JPEG，长边 1280，`q=80`，约 200 KB） | **1 份原图**（长边 **2560 px**，JPEG `q=88`，约 1.5 MB），不在客户端派生副本 |
| 归档主图 | **WebP `q=78`，长边 1280**（服务端转） | **JPEG `q=88`，长边 2560** 原图保留 |
| 展示副本 | 即归档 WebP（同一张） | **WebP `q=80`，长边 1600**（服务端派生，约 300 KB） |
| 缩略图 | 320 px / ~15 KB | 320 px / ~15 KB |
| **单张存档体积** | **约 135 KB**（WebP 120 + 缩略 15） | **约 1.8 MB**（原图 1.5 MB + 展示 0.3 MB + 缩略 15 KB） |
| 客户端 JPEG 是否保留 | **否**（转码后丢弃，只留合成水印图） | 是（即原图） |
| EXIF | 保留 `DateTimeOriginal` / GPS 供稽核，但**不信任**，以服务端为准 | 保留 + 关联 `abnormality_id` / 问题单号 |
| 水印 | **必带**：时间 / 点位 / 姓名工号 / 企业 / GPS / 签名短码；字体 ≥24 px @1280，半透明底条 | **必带**：时间 / 点位 / 人员 + 问题单号；不得遮挡隐患主体 |
| 张数 | **1 张 / 点位 / 次**（补拍上限 2，需填原因） | **1~3 张 / 问题**（全景 1 + 局部特写 ≤2），硬上限 5 |
| 格式禁用 | **禁 PNG**（照片类 PNG 体积可达 JPEG 3~5×） | 同左；纯文字 / 单据截图可用 PNG，须标 `content_type=doc` |
| 加载策略 | 列表只拉缩略图；点开拉 WebP | 列表只拉缩略图；点开拉 WebP 展示图；**仅复核 / 取证才拉原图** |
| 含人脸 | 不适用 | 按 `WX-08` 敏感个人信息处理：缩略图默认模糊、原图访问写 `audit_logs` |
| 保留期（建议） | 90 d 标准 → 低频 → 归档，**不自动删除** | 展示图长期标准；原图 90 d 标准 → 低频 → 归档 |

> **格式选型依据**：WebP 同画质比 JPEG 小 25~35%，小程序基础库 2.9.0+ 全平台支持，iOS 14 以下需降级（`WX-12`）；因此**采集端统一 JPEG（相机直出、EXIF 完整、双端零兼容风险），转码与多副本派生全部放服务端**，客户端不做格式转换。AVIF 虽再小 ~20%，但需基础库 2.16.0+ 且解码更慢，一期不采用。

##### 5.2.8.2 存储成本测算（估算，口径见附录 H）

假设（**全部为建议值**）：逻辑点位 60 个、日频次 2 班 × 30 天 = **3,600 次打卡/月**；问题上报率 5% = 180 单/月 × 2 张 = **360 张随手拍/月**。

| 方案 | 打卡 | 随手拍 | 月增量 | 1 年后存量 | 存储费/月（0.12 元/GB·月） |
|---|---|---|---|---|---|
| **本文方案（压缩 + 派生 + 分层）** | 3,600 × 135 KB ≈ 0.49 GB | 360 × 1.8 MB ≈ 0.65 GB | **≈ 1.13 GB** | **≈ 13.6 GB** | **≈ ¥1.6** |
| 未优化基线（全存 4000×3000 原图 3.5 MB，无派生） | 3,600 × 3.5 MB ≈ 12.6 GB | 360 × 3.5 MB ≈ 1.26 GB | ≈ 13.86 GB | ≈ 166 GB | ≈ ¥19.9 |

**容量节省 ≈ 92%。** 但必须说清：**单看存储费，一年差额只有约 ¥220，不是主要收益**。真正的大头是**流量与调用**：

| 场景（每月 2,000 次列表查看 × 10 张图） | 下行量 | 费用（公网 0.5 元/GB） |
|---|---|---|
| 本文方案：列表只拉 15 KB 缩略图 | 0.3 GB | ≈ **¥0.15** |
| 直接拉 3.5 MB 原图 | 70 GB | ≈ **¥35** |

差约 **230 倍**。此外还省：上行带宽、图片处理调用次数、备份 / 跨地域复制、以及多年多园区累积后的线性增长。这才是「考虑存储成本」要解决的真问题。

### 7.3 设备台账

**V0.3.3 改写**。三份 `S-17` 设备清单是「工程量 + 金额」口径，但**B区保险购买清单与消防设备清单里含完整的大型设施资产清单**（9 类，见附录 G），不只是造价数据。一期建 `facilities` **静态台账 + 人工巡检**：

1. 从 `S-17` 导入 `name / spec / quantity / building / source_doc`，按附录 G 映射 `category`；
2. 补录清单缺失的运行态字段：`facility_id / location / run_status / normal_criteria / vendor / last_service_at / owner / qrcode`；
3. `FIRE` 巡查的 `FACILITY` 子域扫码巡检，人工判定「是否正常运转」，结果写 `facility_inspections` 并关联 `patrol_tasks`；
4. **不接**设备传感器 / IoT 回传（§7.4）。

> 用户举例「高低压电房、消防主控」分别对应 **G1**（#1~#3 电房、高压柜 G01~G05、干式变压器、低压柜 P01~P13）与 **G2**（火灾报警控制器 / 消防联动控制器、消防控制室、各监控主机），实读确认**均在清单内**。

### 7.4 明确不做的集成

门禁、监控、摄像头、电梯物联网、消防主机联网——均不在一期，仅作为现状证据源。

> **V0.3.3 澄清**：本节禁止的是**自动联网与数据回传**，不禁止人工巡查。到消防控制室目视查看主机面板有无故障 / 屏蔽 / 主电故障灯、到电房听异响看仪表，属于 §5.2.6 `FACILITY` 的人工打勾 + 照片，与本节不冲突。

1. 企业档案字段要靠物业逐家补，46 家 × 7 个字段，是最可能拖进度的环节。
2. 检查项字典如果业务方不确认国标/培训值取舍，会反复改。
3. **商户已开 L1 微信账号**（V0.3.1 改），但「双方确认」的签认方式未定：L1 账号能否作为签字一方、还是仍需纸质签名拍照，直接影响 `FR-31` 的闭环完整率（§13 `U3`）。

### 12.3 D8 的完整答案（可直接对外解释）

> 不选 1 h 还是 1.5 h，因为这不是一个数的问题：
> 1. **先看部位**：防火墙上的门 → 甲级；封闭楼梯间、防烟前室、消防电梯前室 → 乙级；竖井 → 丙级。
> 2. **再看标准**：国标甲 1.5/乙 1.0/丙 0.5；培训（1120 表6）甲 2/乙 1.5/丙 1。
> 3. **丙类厂房**：应设**乙级防火门**（原件明文），即国标 1.0 h、培训 1.5 h。
> 4. 清单「丙类 ≥1 h」是把「丙级门 1 h」误当「丙类厂房」，已修正。
> 5. **落地**：国标判合规，培训值判达标；无门铭牌/无认证证书 → 判不合格。

### H.2 成本测算口径（可复算）

| 参数 | 取值 | 性质 |
|---|---|---|
| 逻辑点位数 | 60 | 建议值（`U10`） |
| 日频次班次 | 2（早 / 晚） | `S-05` 两班倒 |
| 月天数 | 30 | 估算 |
| 月打卡次数 | 60 × 2 × 30 = **3,600** | 推导 |
| 问题上报率 | 5% | 建议值 |
| 随手拍张数 | 3,600 × 5% × 2 = **360** | 推导 |
| 未优化基线单张 | 4000×3000 JPEG ≈ 3.5 MB | 相机直出典型值 |
| 优化后单张（打卡） | 120 KB WebP + 15 KB 缩略 ≈ **135 KB** | `WX-12` |
| 优化后单张（随手拍） | 1.5 MB 原图 + 0.3 MB WebP + 15 KB 缩略 ≈ **1.8 MB** | `WX-12` |
| 存储单价 | 0.12 元/GB·月（阿里云 OSS 广州 / 本地冗余） | `WX-13`，**采购当期复核** |
| 公网下行 / CDN 回源 | 0.5 / 0.15 元/GB | `WX-13` |

**复算**：
- 优化后月增量 = 3,600×135 KB + 360×1.8 MB ≈ 0.49 + 0.65 = **1.13 GB/月** → 1 年 ≈ **13.6 GB**
- 基线月增量 = 3,600×3.5 MB + 360×3.5 MB ≈ 12.6 + 1.26 = **13.86 GB/月** → 1 年 ≈ **166 GB**
- 容量节省 ≈ **92%**；存储费差 ≈ (166−13.6)×0.12 ≈ **¥18/月、¥220/年**
- **流量才是大头**：2,000 次/月 × 10 张，缩略图 15 KB → 0.3 GB ≈ ¥0.15；原图 3.5 MB → 70 GB ≈ ¥35，**差 ~230 倍**

| 对象 | 0~90 d | 90~365 d | >365 d |
|---|---|---|---|
| 打卡 WebP + 缩略图 | 标准 | 低频 IA | 归档（不删） |
| 随手拍 WebP 展示图 + 缩略图 | 标准 | 标准 | 标准 |

## 附录 I · 现场问题上报分级速查卡（V0.3.4 新增，可打印张贴）

3. 要整改但不马上出事？ → **L2 一般**（拍照下单）
4. 只是脏乱小瑕疵？ → **L1 提示**（记一笔）

**两条硬口诀**：拿不准**往高报**一级，由队长复核降档；**严禁往低报**。现场只判「多急」，不判「是不是红线」。

| 档 | 色 | 你要做什么 | 典型例子 |
|---|---|---|---|
| **L1 提示** | 蓝 | 拍照记录，交给保洁 / 日常维护，**不建单** | 纸屑落叶、墙面小污迹、非疏散指示灯坏一只、灭火器箱积尘但压力正常 |
| **L2 一般** | 黄 | 拍照 → 建异常单 → 等整改通知（7 天内闭环） | 通道被纸箱临时占用但仍 ≥1.4 m、灭火器压力表黄区、单只应急灯不亮、商户少量纸箱靠墙未堵疏散 |
| **L3 严重** | 橙 | **先管控现场**（隔离 / 停用 / 劝离）→ 立即上报队长 + 工程主管 → 强制建单（24~48 h） | 疏散通道 <1.4 m、消火栓被圈占、配电箱前堆物、安全出口锁闭、防火门常闭失效、商户私拉乱接 / 阁楼堆高、整改逾期或复查不过、**高低压电房异响异味 / 消防主控报故障** |
| **L4 紧急** | 红 | **先拨 119 / 120（如涉及）→ 一键拨值班主管 → 按应急预案疏散 / 断电 / 警戒** | 明火冒烟、燃气味、电线打火 / 配电箱冒烟、消防主机报警确认险情、人员受伤被困、电梯困人、大面积漏水淹电房、可疑人员正在破坏 |

**L4 弹窗顺序**：二次确认（30 s 内可撤销）→ 不可划走的提示条 → 主按钮「一键拨打值班主管」+ 上方并列 119/120 → 同时自动建事件单 + 企微通知 + 记录拨打结果 → 未接提示转第二联系人 → 终点物业经理。

> iOS 提示：点击后微信可能只在顶部显示拨号横幅，请再点一次横幅确认拨打。
> 可疑人员（含 L4）**不生成整改单**，走秩序事件台账并上报值班室；是否报 110 由物业定（`U7`）。照片含人脸按敏感信息处理。

## 〇、四模块通用约定

| 项 | 约定 |
|---|---|
| 编号 | 每单生成「模块码-年月日-流水号」，如 `PL-20261124-001`（放行）、`TK-…`（任务）、`MT-…`（会议）、`CP-…`（投诉） |
| 状态机 | 显式状态 + 白名单迁移，禁止跳转；全部迁移写 `audit_logs` |
| 通知 | 企微应用消息为主，短信兜底；每条通知记「发送-送达-已读」 |
| 留痕 | 关键节点必传照片/签名，服务端记录接收时间 |
| 超时 | 每个「待办态」都有 `deadline`，超时自动升级，不允许静默滞留 |
| 催办 | 同一状态停留超过阈值（建议 2 倍时限）→ 自动催办并计入部门月度统计 |
| 数据保留 | 业务记录 ≥3 年；涉及安全/纠纷的附件 ≥5 年（待确认，与消防记录保存期对齐） |

## 一、物品放行（`PL`）

### 1.1 依据：现行纸质表单

用户提供的《租户大件物品出场申请表》（金峰兆业时尚产业社区客户服务中心）字段：

| 区块 | 字段 |
|---|---|
| 申请 | 申请单位、物品搬运人、联系电话、车牌号码、申请放行日期/时间 |
| 物品 | 搬运物品清单（多条） |
| 授权 | 单位放行授权人 |
| 审核 | 营运部审核、审核日期/时间 |
| 核对 | 值班员核对、放行日期/时间 |
| 联次 | 第一联 客户服务中心（白）、第二联 安管部（红） |

纸质单自带 4 条规则，**直接升级为系统校验**：
1. 所搬物品必须与所填物品相符，否则不予放行 → 逐项核对打勾，有一项不符即整单拒绝
2. 超出约定放行时间，此表无效，须重新申请 → 超时自动失效，不允许「延用旧单」
3. 秩序员须对物品进行检查、核对后予以放行 → 核对是放行的**前置强制节点**，不能先放后补
4. 大件物品必须在规定的路线、时段搬运 → 路线/时段做成园区配置项

### 1.2 状态机

| 状态 | 代码 | 含义 | 谁可以进入 |
|---|---|---|---|
| 待提交 | `PL_DRAFT` | 商户填写中 | 商户/客服代填 |
| 待审核 | `PL_REVIEW` | 已提交，等营运部 | 商户提交 |
| 待放行 | `PL_READY` | 审核通过，等搬运 | 营运部审核通过 |
| 待核对 | `PL_CHECK` | 搬运人到场，值班员核对中 | 值班员开始核对 |
| 已放行 | `PL_DONE` | 核对通过并放行（终态） | 值班员确认放行 |
| 已驳回 | `PL_REJECT` | 审核不通过 | 营运部驳回 |
| 已失效 | `PL_EXPIRED` | 超约定时间未放行（终态） | 系统定时 |
| 已取消 | `PL_CANCEL` | 申请方撤回（终态） | 商户/客服 |

| # | 迁移 | 触发 | 角色 | 校验 |
|---|---|---|---|---|
| P-1 | DRAFT → REVIEW | 提交 | 商户/客服 | 申请单位、搬运人、电话、车牌、时间、物品清单（≥1 条）、授权人齐全 |
| P-2 | REVIEW → READY | 审核通过 | 营运部 | — |
| P-3 | REVIEW → REJECT | 驳回 | 营运部 | 驳回原因必填 |
| P-4 | READY → CHECK | 搬运人到场 | 值班员 | 当前时间在约定放行时段内 |
| P-5 | CHECK → DONE | 核对通过 | 值班员 | **逐项核对全部打勾** + 现场照片 ≥1 张 |
| P-6 | CHECK → REJECT | 物品不符 | 值班员 | 填不符项 + 照片，转异常记录 |
| P-7 | READY/CHECK → EXPIRED | 超时 | 系统 | 超过约定时间 + 宽限（建议 2 h） |
| P-8 | 任意非终态 → CANCEL | 撤回 | 商户/客服 | 填原因 |

### 1.3 字段清单

`apply_unit`（申请单位，关联企业档案）、`carrier_name`、`carrier_phone`、`plate_no`、`planned_time`、`items[]`（name/qty/spec/photo）、`authorized_by`（单位授权人）、`reviewer`、`reviewed_at`、`checker`、`checked_at`、`photos[]`、`route`、`time_window`、`status`、`reject_reason`

### 1.4 异常分支

| 场景 | 处理 |
|---|---|
| 物品与申报不符 | 拒绝放行，记录不符项；同一单位 30 天内 2 次 → 通报营运部 |
| 超时到场 | 单据失效，要求重新申请（不允许后台改时间） |
| 无授权人签字 | 不予受理，退回补签 |
| 疑似危险品/违禁品 | 立即停止放行，上报秩序队长 + 物业经理，按危化品流程处置 |
| 夜间/非工作时段 | 需值班领导审批（待确认是否允许） |

### 1.5 待确认

- ~~是否需要商户端自助申请（还是客服代填）~~ → **V0.3.1 已定**：商户用微信登录（L1）自助申请，客服代填仅作兜底；仍需确认 L1 提交是否必须经营运部审核前置（见 PRD V0.3.1 §4.8.4）
- 大件物品的判定标准（尺寸/重量阈值）
- 规定路线与时段的园区平面依据
- 电子单是否取代纸质两联（消防/审计是否接受电子留档）

## 二、日常任务（`TK`）

### 2.1 现状与差距

`物业11月月度工作计划表` 已有 41 条任务（含周期性：抄表 2 号前、电梯保养每月 2 次、强电周检等），但只是 Excel 台账，没有分派、提醒、验收、留痕。**本模块是把这张表搬进系统并补上闭环。**

### 2.2 任务类型

| 类型 | 说明 | 生成方式 |
|---|---|---|
| 临时任务 | 一次性，临时指派 | 手工建单 |
| 周期任务 | 日/周/月/季/年重复 | 按规则自动生成子任务 |
| 专项任务 | 有明确起止和验收标准的项目（如消防整改） | 手工建单 + 里程碑 |

### 2.3 状态机

| 状态 | 代码 | 说明 |
|---|---|---|
| 待分配 | `TK_NEW` | 已建单，未指定执行人 |
| 待执行 | `TK_ASSIGNED` | 已指派 |
| 执行中 | `TK_DOING` | 执行人已开始 |
| 待确认 | `TK_CONFIRM` | 执行人提交完成，等确认 |
| 已完成 | `TK_DONE` | 确认通过（终态） |
| 已退回 | `TK_REJECT` | 确认不通过 |
| 已逾期 | `TK_OVERDUE` | 超截止未完成 |
| 已取消 | `TK_CANCEL` | 任务取消（终态） |

| # | 迁移 | 触发 | 角色 | 校验 |
|---|---|---|---|---|
| K-1 | NEW → ASSIGNED | 分配 | 发起人（主管） | 指定执行人 + 截止时间 |
| K-2 | ASSIGNED → DOING | 开始 | 执行人 | — |
| K-3 | DOING → CONFIRM | 提交完成 | 执行人 | 完成说明必填；关键任务需照片 |
| K-4 | CONFIRM → DONE | 确认 | 发起人/上级 | 操作人 ≠ 执行人 |
| K-5 | CONFIRM → REJECT | 退回 | 发起人/上级 | 原因必填 |
| K-6 | REJECT → DOING | 重新执行 | 执行人 | — |
| K-7 | ASSIGNED/DOING → OVERDUE | 超期 | 系统 | 超过 deadline |
| K-8 | OVERDUE → CONFIRM | 补做提交 | 执行人 | 记 `is_overdue=true`，仍计入逾期率 |
| K-9 | 任意非终态 → CANCEL | 取消 | 发起人/物业经理 | 原因必填 |

### 2.4 字段与通知

字段：`title`、`desc`、`type`（临时/周期/专项）、`recurrence`（RRULE 或简化为 日/周/月/季/年 + 间隔）、`deadline`、`priority`、`assignee`、`collaborators[]`、`attachments[]`、`completion_note`、`photos[]`、`confirm_by`、`status`

通知：分配即通知执行人 → 截止前 1 天提醒 → 逾期当日升级至发起人 → 逾期 3 天升级至物业经理。

### 2.5 与巡查的区别（避免两套东西打架）

| 维度 | 巡查任务 | 日常任务 |
|---|---|---|
| 有无固定检查项 | 有（检查项字典） | 无，自由描述 |
| 结果形态 | 逐项打勾 + 数值 | 完成/未完成 + 说明 |
| 复核 | 必须（R2 复核） | 必须（发起人确认） |
| 是否计入考核 | 计入准时完成率 | 计入任务完成率 |

> 同一个「消防设施月检」如果既在巡查模板里又在任务表里，会重复计数。**规则：凡有检查项的走巡查，无检查项的走任务，不允许两边都建。**

## 三、会议预约（`MT`）

### 3.1 现状

园区目前无会议室预约系统，会议靠口头/群里喊。会议纪要显示有周例会、专题会。**这是纯新增，没有现状流程可依，全部为建议方案。**

### 3.2 状态机

| 状态 | 代码 | 说明 |
|---|---|---|
| 待审批 | `MT_PENDING` | 已提交，等审批（小会议室可免审批） |
| 已预约 | `MT_BOOKED` | 审批通过，锁定资源 |
| 进行中 | `MT_ONGOING` | 到开始时间 |
| 已结束 | `MT_ENDED` | 到结束时间（终态） |
| 已取消 | `MT_CANCEL` | 申请人取消（终态） |
| 已驳回 | `MT_REJECT` | 审批不通过 |
| 冲突 | `MT_CONFLICT` | 时间冲突，需改期 |

### 3.3 关键规则

1. **资源冲突检测**：同会议室、时间区间重叠即拒绝，不允许「先到先得式覆盖」。
2. **免审批额度**：≤2 小时且 ≤6 人的小会可直接预约（待确认）。
3. **周期会议**：支持「每周一 9:00」类重复预约，一次占用整个周期，可单次改期。
4. **爽约管理**：预约后 15 分钟内无人签到 → 标记爽约并释放资源；同一部门月爽约 3 次 → 限制预约（待确认是否要做）。
5. **会前提醒**：开始前 15 分钟推送参会人。

### 3.4 字段

`subject`、`room_id`、`start_at`、`end_at`、`organizer`、`attendees[]`、`agenda`、`attachments[]`、`recurrence`、`checkin_at`、`status`

### 3.5 待确认

- 园区有几间会议室、各自容量与设备（投影/视频会议）
- 是否需要审批、审批人是谁
- 外部人员（商户/访客）能否预约
- 是否与企微日程打通（推荐打通，避免两套日历）

## 四、投诉建议（`CP`）

### 4.1 现状

考核表已有「投诉/报修事项月度闭环率 100%」的考核口径，但**没有成文流程**：谁受理、多久响应、怎么回访、超时怎么办，全是空白。

### 4.2 状态机

| 状态 | 代码 | 说明 |
|---|---|---|
| 待受理 | `CP_NEW` | 已登记，未确认受理 |
| 已受理 | `CP_ACCEPTED` | 客服确认受理并分类分级 |
| 处理中 | `CP_DOING` | 已转责任部门 |
| 待回访 | `CP_VISIT` | 处理完成，等回访 |
| 已关闭 | `CP_CLOSED` | 回访完成且诉求人认可（终态） |
| 已升级 | `CP_ESCALATED` | 超时或重大，上报经理 |
| 已转办 | `CP_TRANSFER` | 不属物业职责，转相关方并告知 |
| 已作废 | `CP_VOID` | 无效/重复/恶意（终态） |

### 4.3 分类分级与时限（建议值）

| 维度 | 取值 | 时限 |
|---|---|---|
| 类型 | 投诉 / 建议 / 咨询 / 表扬 | — |
| 级别 | 一般 | 受理 2 h、处理 72 h、回访 24 h |
| 级别 | 紧急（影响经营/安全） | 受理 30 min、处理 24 h |
| 级别 | 重大（人身安全/群体/媒体/监管） | 立即上报物业经理，1 h 内响应，当日出具处置方案 |

### 4.4 关键规则

1. **首问负责**：第一个接到投诉的人负责登记，不得以「不归我管」推诿。
2. **与工单联动**：投诉内容涉及维修的，自动生成工单，工单完成后回填投诉记录，**不重复建单**。
3. **回访必做**：关闭前必须回访，记录「满意/基本满意/不满意」；不满意 → 退回处理中，不允许直接关闭。
4. **重大投诉双报**：同时报物业经理与运营负责人。
5. **闭环率口径**：`CP_CLOSED / (CP_CLOSED + 超时未关闭) × 100%`，与考核表「投诉报修闭环率 100%」对齐。

### 4.5 字段

`source`（电话/企微/现场/小程序）、`type`、`level`、`content`、`complainant`、`contact`、`expect_time`、`assignee`、`dept`、`records[]`（处理过程）、`visit_result`、`satisfaction`、`ticket_id`（关联工单）、`status`

### 4.6 待确认

- 投诉受理入口（是否开放商户自助提交）
- 是否需要匿名投诉
- 满意度评价是否对外可见（影响考核公正性）
- 重大投诉的判定权在谁

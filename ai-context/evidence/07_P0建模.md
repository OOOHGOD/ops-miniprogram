**三个必须明确的设计约束**（来自 `AG-01`、`AG-02`、`AG-04`）：
1. **R1 不能自己复核自己的记录**（第 5 行），否则「未提示视为失职」无法留证。系统层面要做「操作人 ≠ 复核人」校验。
2. **R3 邓令升不是外包**（V0.3.2 用户勘误：他是管理外协维保单位的物业方管理岗；外包的是 R8 外协作业人员）。但仍必须配 **代理验收人**（建议：刘振强代理），字段 `actingApprover`——理由是防 R3 休假/离职/**岗位空缺**断链（`AC-01` 纪要曾记「空缺待招」），与是否外包无关。
3. **R7 商户登录（V0.3.1 已关闭）**：用户 2026-11-24 拍板「商户用微信登录即可」。商户 = **微信登录 L1 + 后台审核绑定 `enterprise_id`**，不开放自助注册、不强制手机号；R8 外协一期仍不开账号。**仍待确认**：商户 L1 账号能否作为「双方确认」的一方线上签字（PRD §13 `U3`）。

## 二、巡查任务状态机（`AG-05`）

### 2.1 状态定义

| 状态 | 代码 | 含义 | 是否终态 |
|---|---|---|---|
| 待开始 | `PENDING` | 已生成任务，未到/刚到时段 | 否 |
| 进行中 | `IN_PROGRESS` | 已开始，未提交 | 否 |
| 待复核 | `PENDING_REVIEW` | 已提交，等 R2 复核 | 否 |
| 已通过 | `APPROVED` | 复核通过，计入完成率 | **是** |
| 已驳回 | `REJECTED` | 复核不通过，需重做 | 否 |
| 已逾期 | `OVERDUE` | 超过截止时间未提交 | 否 |
| 已作废 | `VOID` | 计划取消（天气/临时任务调整） | **是** |

### 2.2 迁移规则

| # | 当前 | 触发动作 | 执行角色 | 前置条件 | 下一状态 | 留痕要求 |
|---|---|---|---|---|---|---|
| T-01 | PENDING | 开始巡查 | R1 | 在任务时段内（或提前 N 分钟，建议 15） | IN_PROGRESS | 记录开始时间（服务端） |
| T-02 | PENDING | 系统定时扫描 | 系统 | 超过时段截止仍未开始 | OVERDUE | 自动写入 `overdue_reason=未开始` |
| T-03 | IN_PROGRESS | 提交记录 | R1 | 必填项齐全（见 §5.3） | PENDING_REVIEW | 记录提交时间、照片数、离线标记 |
| T-04 | IN_PROGRESS | 系统定时扫描 | 系统 | 超过截止时间 | OVERDUE | 自动写入 |
| T-05 | PENDING_REVIEW | 复核通过 | R2 | 操作人 ≠ 提交人 | APPROVED | 复核人、复核时间、意见（可空） |
| T-06 | PENDING_REVIEW | 复核驳回 | R2 | 必须填驳回原因 | REJECTED | 驳回原因必填（≥10 字） |
| T-07 | REJECTED | 重新提交 | R1 | 已修改被驳回项 | PENDING_REVIEW | 记录驳回-重提耗时 |
| T-08 | OVERDUE | 补录 | R1 | 需填补录原因 + R2 审批 | IN_PROGRESS | `is_supplement=true`，原因必填，审批人留痕 |
| T-09 | PENDING/IN_PROGRESS | 作废 | R4 | 必须填作废原因 | VOID | 作废人、原因必填 |
| T-10 | VOID | 恢复 | R4 | — | PENDING | 记录恢复人与原因 |

### 2.3 完成率口径（必须先定，否则考核打架）

| 指标 | 分子 | 分母 | 排除项 | 依据 |
|---|---|---|---|---|
| 准时完成率 | `APPROVED` 且 `submit_time ≤ deadline` | 应完成任务数 | `VOID` 不计入分母 | `BP` 设计盲区、`L-C5` |
| 任务完成率 | `APPROVED` | 应完成任务数 | `VOID` 不计入 | 同上 |
| 逾期率 | `OVERDUE` 过（含后来补录通过） | 应完成任务数 | `VOID` 不计入 | 同上 |

> **注意**：补录（T-08）即使最后 `APPROVED`，**仍计入逾期率**，只是不计入「未完成」。否则补录就是洗白通道。`AG-05` 明确要求区分。

## 三、异常 → 整改闭环状态机（`AG-06`、`AG-15`）

### 3.1 分级规则（三档）

| 档位 | 判定依据 | 处置动作 | 时限（建议值） |
|---|---|---|---|
| **红线项** | 见 §3.2 清单，或数值判定为「不达标」且 `is_redline=true` | 强制生成工单 + 立即通知 R4 + 下发整改通知书 | 24 小时内整改，逾期自动升级 |
| **一般项** | 非红线的不合格项 | 生成整改通知书，按流程走 | 7 天内整改 |
| **观察项** | 轻微、可现场纠正、或标准待核项 | 只记录 + 拍照，不生成整改单 | 连续 3 次同类 → 自动升级为一般项 |

### 3.2 红线项清单（建议值，依据 `L-R2` + `M-02` + `S-04` 考核扣分项）

1. 消防通道 / 疏散通道被占用、堵塞（数值 < 1.4 m，见 `GB-09`）
2. 消火栓无水、被圈占遮挡
3. 配电房异响、配电箱前堆物
4. 危化品超量（> 3–5 桶 或 > 80 kg）
5. 安全出口锁闭、被封堵
6. 防火门被拆除/常开无闭门器/等级不符（见 `GB-11`）
7. 喷淋头被喷涂、损坏
8. 消防报警后未按时到场（3 分钟，`S-04` 考核口径）

> 待确认：这份清单是否完整、第 8 条属「行为红线」还是「结果红线」，需 R4 确认。

### 3.3 状态定义与迁移

| 状态 | 代码 | 含义 |
|---|---|---|
| 待分级 | `E_PENDING` | 异常已生成，未定档 |
| 已分级 | `E_GRADED` | 已定红线/一般/观察 |
| 已下发 | `E_ISSUED` | 整改通知书已下发 |
| 整改中 | `E_FIXING` | 责任方已响应 |
| 待复查 | `E_REVIEW` | 责任方回传整改结果 |
| 已关闭 | `E_CLOSED` | 复查通过（终态） |
| 已升级 | `E_ESCALATED` | 逾期未整改，上报 R4 |
| 已作废 | `E_VOID` | 误报（终态） |

| # | 当前 | 触发 | 角色 | 条件 | 下一状态 |
|---|---|---|---|---|---|
| E-01 | E_PENDING | 定档 | R2 | 选红线/一般/观察 + 填判定说明 | E_GRADED |
| E-02 | E_GRADED | 下发整改单 | R2 | 红线/一般；填责任方、期限 | E_ISSUED |
| E-03 | E_GRADED | 转观察记录 | R2 | 仅观察项 | E_CLOSED（标 observation） |
| E-04 | E_ISSUED | 责任方响应 | R8/R7/R1 | — | E_FIXING |
| E-05 | E_FIXING | 回传整改结果 | 责任方 | 至少 1 张整改后照片 | E_REVIEW |
| E-06 | E_REVIEW | 复查通过 | R2 | 操作人 ≠ 整改人 | E_CLOSED |
| E-07 | E_REVIEW | 复查不通过 | R2 | 填不通过原因 | E_ISSUED（期限顺延，记第 2 次） |
| E-08 | E_ISSUED/E_FIXING | 超期未整改 | 系统 | 超过期限 | E_ESCALATED + 通知 R4 |
| E-09 | E_ESCALATED | 升级处置（停水停电/上报） | R4 | 需审批留痕 | E_ESCALATED（记处置结果） |
| E-10 | E_PENDING/E_GRADED | 作废 | R4 | 填误报原因 | E_VOID |

**关键设计点**：红线项**不允许**走 E-03 转观察，也不能由 R2 单方面关闭，必须 R4 知会。这是 `AG-15` 要求的「红线不可降级」。

## 四、工单状态机（`AG-07`）

### 4.1 「双方确认」与「独立验收」的关系（`X` 冲突的正面回答）

开发计划 v2.0 写**「独立验收」**（物业方独立于处理方验收），评审意见写**「双方确认」**（外包维保需现场跟随、结果当场确认、验收单双方签认）。这两句**不是矛盾的，是两种验收模式**：

| 模式 | 代码 | 适用 | 验收要求 |
|---|---|---|---|
| 单方验收 | `internal` | 内部工单（秩序/工程/保洁自己处理） | 派单人或主管验收即可 |
| 双方确认 | `joint` | 外协工单（消防维保、电梯维保、第三方检测） | **处理方签认 + 物业方签认，两个签名齐全才可完成** |

字段：`tickets.accept_mode ∈ {internal, joint}`，由派单时按处理人类型自动判定（外协 → joint）。

### 4.2 状态与迁移

| 状态 | 代码 | 含义 |
|---|---|---|
| 待派单 | `T_NEW` | 工单已建，未指定处理人 |
| 待接单 | `T_ASSIGNED` | 已通知处理人，未响应 |
| 处理中 | `T_DOING` | 已接单 |
| 待验收 | `T_ACCEPT` | 处理完成，等验收 |
| 待双方确认 | `T_JOINT` | 外协场景，等第二个签名 |
| 已完成 | `T_DONE` | 验收通过（终态，可归档） |
| 已关闭 | `T_CLOSED` | 归档（终态） |
| 已逾期 | `T_OVERDUE` | 超处理时限 |
| 已取消 | `T_CANCEL` | 误报/重复（终态） |

| # | 当前 | 触发 | 角色 | 条件 | 下一状态 |
|---|---|---|---|---|---|
| W-01 | T_NEW | 派单 | R3 | 选处理人/外协；设时限 | T_ASSIGNED |
| W-02 | T_ASSIGNED | 接单 | R1/R8 | — | T_DOING |
| W-03 | T_ASSIGNED | 超时未接单 | 系统 | 超首响时限（建议 30 分钟） | T_OVERDUE + 升级 |
| W-04 | T_DOING | 提交完成 | R1/R8 | 必填处理说明 + 照片 | T_ACCEPT 或 T_JOINT（按 accept_mode） |
| W-05 | T_ACCEPT | 验收通过 | R3 | — | T_DONE |
| W-06 | T_ACCEPT | 验收驳回 | R3 | 填原因 | T_DOING |
| W-07 | T_JOINT | 外协方签认 | R8 | 手写签名 + 姓名 | T_JOINT（等物业） |
| W-08 | T_JOINT | 物业方签认 | R4/R3 | 手写签名 + 姓名 | T_DONE（两签齐全） |
| W-09 | T_JOINT | 任一方拒签 | R8/R4 | 填拒签理由 | T_DOING |
| W-10 | T_DOING | 超处理时限 | 系统 | — | T_OVERDUE |
| W-11 | 任意非终态 | 取消 | R3/R4 | 填原因 | T_CANCEL |
| W-12 | T_DONE | 归档 | 系统/定时 | 完成后 N 天 | T_CLOSED |

**「双方确认」的判定逻辑必须写死**：`joint` 模式下，`T_JOINT → T_DONE` 需要 `signature_count == 2`，缺一个就停在 T_JOINT 并计时。这条防的是「外协自己点完成、物业没到现场」——正是 `S-04` 扣分项「高空坠物隐患未排除致事故」想堵的漏洞。

## 五、数值判定规则（`AG-13`、`AG-14`、`AG-15`）

### 5.1 检查项字典的 9 个字段

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `item_code` | string | 检查项编码 | `FIRE_DOOR` |
| `item_name` | string | 名称 | 防火门 |
| `judge_mode` | enum | `auto` / `manual` / `none` | `manual`（按部位定级） |
| `norm_ref` | string | 规范出处 | `GB 55037-2022 6.4.2/6.4.3` |
| `threshold` | json | 阈值（可多档） | `{"甲级":1.5,"乙级":1.0,"丙级":0.5}` |
| `unit` | string | 单位 | `h` |
| `is_redline` | bool | 不达标是否红线 | `true` |
| `enterprise_value` | json | 企业加严值（与国标不同的） | `null` |
| `credibility` | enum | `国标一致` / `待核` / `不一致` / `企业口径` | `国标一致` |

> 完整 16 行取值见 `06_标准规范对照表.md`。

### 5.2 三种判定方式的执行规则

| 方式 | 适用条数 | 系统行为 | 不达标后果 |
|---|---|---|---|
| `auto` | 5 条（GB 一致） | 自动比对数值 → 判定合格/不合格 | `is_redline=true` → 自动建红线异常 + 通知 R4；否则建一般异常 |
| `manual` | 4 条（待核） | 只记录数值/照片，由人点「合格/不合格」 | 人工判不合格 → 按人工选的档位处理 |
| `none` | 2 条（企业口径） | 只记录 + 拍照，不判定 | 无自动后果 |

### 5.3 提交前的必填校验（防漏项）

| 场景 | 必填 | 校验失败提示 |
|---|---|---|
| 每个检查项 | 结果（合格/不合格/不适用） | 「第 X 项未填结果」 |
| `judge_mode=auto` 的项 | 数值 | 「第 X 项需填数值，单位 cm」 |
| 不合格项 | 隐患描述（≥10 字）+ 照片 ≥1 张 | 「不合格项必须说明并拍照」 |
| 红线项 | 照片 ≥2 张（全景 + 特写） | 「红线项需全景与特写各一张」 |
| 全部项 | 位置（自动/手动） | 「无法获取位置，请手动选择点位」 |

### 5.4 「不达标是否自动转整改单」（`L-D4` 原始问题）

**分级回答，不搞一刀切**：

| 条件 | 是否自动转单 |
|---|---|
| `credibility=国标一致` 且 `is_redline=true` 且数值触发 | **是**，自动建红线异常 + 强制通知 R4 |
| `credibility=国标一致` 且非红线 | 是，建一般异常，不强制通知 R4 |
| `credibility=待核` | **否**，生成「待人工判定」提示，由 R2 决定 |
| `credibility=不一致` | **否**，且界面上必须提示「该标准与国标冲突，已标记待修正」 |
| `credibility=企业口径` | 否，只记录 |

> 这样设计的理由：`06` 表里 5 条与国标不一致、4 条待核，如果一律自动转单，系统会拿错标准去罚人，比不做还糟。

## 五、身份与登录门禁（V0.3.1 新增，2026-11-24 用户决策）

> 完整模型见 PRD V0.3.1 §4.8；本节只给 RACI 与门禁的衔接关系。

| 用户原话（`U-D`） | 落地 |
|---|---|
| 巡查必须企微登录 | 巡查模块 L2 门禁，服务端校验 `qy_userid`；L1 一律拦截 |
| 随手拍必须微信登录 | 随手拍以有效 `openid` 为最低门槛；**企微内 `wx.login` 亦可用**，故 L2 自动满足，闭环不断 |
| 企微登录者权重大 | 新增 `auth_level ∈ {L1, L2}`，L2 > L1 |
| 主入口企微工作台 + 双环境适配 | 不勾「仅在企业微信运行」；企微取 userid + openid，微信只取 openid |
| 商户用微信登录 | R7 = L1 账号 + 后台审核绑定企业档案 |

**与 RACI 的关系**：角色（R1~R8）与身份等级（`auth_level`）**正交**。RACI 决定「谁做什么动作」，门禁决定「能不能进这个模块」。例：R2 队长从微信打开（L1 会话）仍不能复核，必须回企微；R7 商户即便有账号也不能复核、关单、签发整改单。

**必须服务端执行的 4 条**（对应 PRD `FR-61`~`FR-64`）：
1. `environment === "wxwork"` 才允许 `wx.qy.login`；微信端禁用。
2. `qy_userid` 每次会话向企微校验有效性，失效降 L1 并写 `audit_logs`。
3. 巡查全链（领取 / 打勾 / 复核 / 作废 / 下发整改单 / 关单 / 报表）L2 专属。
4. 前端隐藏菜单不算门禁。

**合规**：本项目属「体验范围特定」，首页需写明使用范围、静默鉴权、提供「暂不登录」；禁止一进入就弹手机号、隐私协议默认勾选、拒绝授权即拒绝全部服务。内部靠 userid、商户靠审核绑定，均不收手机号。

## 七、巡查二维分类衔接（V0.3.3，用户 `U-D7`）

> 完整模型见 PRD V0.3.3 §5.2.0 / §5.2.6、附录 G、`09_巡查分类与大型设施台账.md`。本节只说明**对状态机 / RACI / 门禁的影响**——结论是：**三套状态机一个都不用改**。

| 维度 | 取值 | 与既有建模的关系 |
|---|---|---|
| `patrol_type` 内容类型 | `DAILY_ORDER` / `FIRE` | 新增任务标签，**不改巡查任务 7 态**（§4.2） |
| `frequency` 频次 | 日 / 周 / 月 | 原有三级，仅**改称**「日频次/周频次/月频次」，不与类型绑定 |
| `fire_domain` 消防子域 | `EQUIPMENT` / `TENANT` / `RECTIFY` / `FACILITY` | 新增检查项分组标签 |

**逐条衔接结论**：

1. **门禁不变**：两类巡查都属「巡查全链」，一律 **L2 企微专属**（§4.8.4、`FR-62`）。商户 L1 不参与打勾。
2. **`TENANT` 子域不改 RACI**：商户需「在场 + 确认签名」，但商户是 L1、**只做签认，不是巡查执行人**；执行人仍是 R1（秩序队员 / 工程岗），复核仍是 R2。`FR-70` 加的是授权与留痕，不是新角色。
3. **`RECTIFY` 子域复用 §4.3 状态机**：「消防整改是否完成」= `abnormalities` 的「待复查 → 已关闭」环节，**不新建检查项、不新建工单、不重复建单**（`FR-71`）。复查不通过退回「已下发」并计次，沿用原规则。
4. **`DAILY_ORDER` 的可疑人员走独立台账**：`DO-03`/`DO-04` 记入 `security_incidents`，**不进异常三档分级、不生成整改通知书**。这是与 §4.3 并行的一条秩序链路（`U7`）。
5. **`FACILITY` 子域新增实体**：`facilities` + `facility_inspections`，人工目视判定，不接 IoT（§7.4）。巡检记录关联 `patrol_tasks`，不改变任务状态机。
6. **快照变双键**：`checkItemsSnapshot` 从「频次」单键改为「类型 + 频次」双键，检查项字典 9 → 12 字段（加 `patrol_type`/`fire_domain`/`target_type`），防历史统计被改字典污染（`FR-09` 扩展）。

**新增 FR-67~73**（PRD §5.8）：二维模型、`DO-01~04`、四子域、商户入内授权、整改复查联动、设施台账、分维度报表。FR 总数 66 → 73。

**`AC-11` 术语裁决**：「日常巡查」由内容类型专用；原频次级别改称「日频次」。同类未决项还有 `AC-10`（「随手拍」双义），建议后续统一出一份术语表。
